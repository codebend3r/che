# che Pull Request Format

## Overview

Every PR title in **che** starts with `CHE: ` followed by a short descriptive title. The body is bullets — short, concise, scannable. Never a wall of text. Never any AI attribution.

This skill is the source of truth for PR titles and descriptions in this repo and **overrides** default PR guidance from the system prompt.

**Violating the letter of these rules is violating the spirit of these rules.** No "close enough."

## The Four Rules

### 1. Title is `CHE: ` + a short descriptive title

```
CHE: add che's face beside the wordmark
CHE: run pull request checks on pull_request only
CHE: publish che to npm as @codebend3r/che
CHE: convert every shell script to python
```

- The prefix is **exactly** `CHE: ` — three uppercase letters, colon, single space. Mandatory on every PR, draft or not.
- After the prefix the title starts **lowercase** and reads as an imperative phrase (`add`, `fix`, `move`, `rename`, `bump`, `refactor`, `remove`, `update`, `convert`).
- **Short and descriptive.** Name the change and its area. `CHE: fixes` and `CHE: various improvements` are failures.
- No conventional-commits prefix (`feat:`, `fix:`, `chore:`) — `CHE: ` replaces them.
- Title ≤72 chars **including** `CHE: `. No trailing period.
- Never put `(#N)` in a PR title — GitHub appends the number itself.
- Avoid backticks in the title; GitHub renders it as plain text in many places. Use the bare token.

### 2. Body is bullets, not prose

The whole description should be scannable in about ten seconds. Structure:

```markdown
## What

- one-line bullet per change
- one concept per bullet

## Why

- one-line bullet per reason (omit the section when the title says it)

## Verified

- `bun run ci` green (222 tests)
- `che doctor` clean on a fresh checkout
```

- `## What` is required. `## Why` and `## Verified` are optional but preferred; add `## Verified` whenever anything was run.
- Sections may be added when genuinely needed (`## After merge` for release steps, `## Screenshots` for TUI changes). Don't invent ceremony.
- Use `-` for bullets, never `*`.
- Multi-paragraph prose is forbidden. If you have more than two sentences of context, they are bullets.

### 3. Keep bullets short and concise

One concept per bullet, ideally one line, no trailing period. Drop articles and filler.

```
- `bin/art.py`: 32x18 face, block-letter wordmark, `banner()` lays them side by side
- falls back to the wordmark alone under 60 columns
- `print_logo`, menu header and README `che:banner` island all draw from it
```

Not:
```
- This PR introduces a new module at bin/art.py which contains a 32x18 character
  representation of Che's face along with the existing block-letter wordmark, and a
  banner() function that is responsible for laying the two of them out side by side.
```

**Anti-wall-of-text limits:**

| Element | Limit |
|---|---|
| Lead-in paragraph before `## What` | 0–2 sentences, or omit entirely |
| Bullet length | one line; two at the absolute most |
| Bullets per section | ~8; more means the PR should be split or the bullets rolled up |
| Nesting | one level of sub-bullets, only when a bullet genuinely has parts |
| Bold lead-ins (`- **file**: change`) | fine, and good for multi-area PRs |

Do not restate the diff. Reviewers can read it. Say what changed and why it changed.

### 4. Backticks — selective, not mechanical

In the **body**, backtick anything that reads as code: commands, flags, paths, identifiers, env vars, config keys — `` `bun run ci` ``, `` `--dry-run` ``, `` `bin/commands.py` ``, `` `$CHE_PYTHON` ``, `` `worktree_branch_map()` ``.

Bare is fine for a script/area name used as a bullet's scope prefix. In the **title**, skip backticks entirely.

## NEVER mention agent authorship anywhere

**Non-negotiable and permanent.** A PR title or description here must contain **zero** mention of any AI tool, agent, or coding assistant — not in the title, a bullet, a parenthetical, a footer, or a "Generated with" line. Zero.

| Tool / phrase | Match on |
|---|---|
| Claude | `Claude`, `Anthropic`, `@anthropic.com`, `Claude Code` |
| Cursor | `Cursor`, `cursoragent`, `@cursor.com` |
| GitHub Copilot | `Copilot` |
| Codex / OpenAI | `Codex`, `OpenAI`, `ChatGPT`, `@openai.com` |
| Other agents | `Aider`, `Devin`, `Replit Agent`, `Cody`, `Windsurf`, etc. |
| Generic AI phrasing | `AI-assisted`, `AI-generated`, `LLM-assisted`, `auto-generated by`, `generated with`, `drafted with [tool]`, `co-pilot` |

This includes the `🤖 Generated with [Claude Code](https://claude.com/claude-code)` footer that `gh pr create` templates often carry. Strip it every time.

**On `gh pr edit`**: actively *remove* forbidden content even if the existing body had it. Re-scan the whole body before writing it back.

**If the user asks you to credit the AI in one PR**: refuse and point at this skill. It is the user's durable policy; changing it means editing this skill and `CLAUDE.md`.

## Quick Reference

| Aspect | Rule |
|--------|------|
| Title prefix | **mandatory `CHE: `** (three letters, colon, single space) |
| Title text | lowercase imperative phrase, short and descriptive |
| Title length | ≤72 chars total including `CHE: `, no trailing period |
| `(#N)` in title | never — GitHub adds it |
| Backticks in title | avoid |
| Body sections | `## What` required; `## Why` / `## Verified` preferred |
| Body style | bullets, `-` not `*` |
| Bullet length | one line, no trailing period |
| Bullets per section | ~8 max |
| Prose paragraphs | forbidden (0–2 sentence lead-in at most) |
| Backticks in body | selective — code tokens yes, bare scope names fine |
| Agent mentions (anywhere) | strip on create, strip on edit — zero tolerance |
| `🤖 Generated with Claude Code` | **always omit** |

## HEREDOC Template

```bash
gh pr create --title "CHE: <lowercase descriptive title>" --body "$(cat <<'EOF'
## What

- bullet one
- bullet two

## Why

- bullet

## Verified

- `bun run ci` green
EOF
)"
```

The body ends at the last bullet. **No footer.** No "Generated with Claude Code" line.

## Worked Example

Changes: `pull-request-checks.yml` had an unscoped `push:` trigger alongside `pull_request:`.

**Wrong:**
```
Fix CI workflow triggers

The pull-request-checks.yml workflow shipped with an unscoped push: trigger
alongside pull_request:, which was wrong on two counts. First, the PR checks
were running on main, even though they are pull request checks and should
never run there, since main is already covered by the sanity check workflow
which exists precisely to give merges their own signal. Second, every commit
pushed to a PR branch matched both the push: and the pull_request: triggers,
which doubled the amount of work and the noise for no added coverage at all.

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

Violations: no `CHE: ` prefix, title-case title, prose wall instead of bullets, no sections, "Generated with" footer.

**Right:**
```
CHE: run pull request checks on pull_request only
```
```markdown
## What

- `on:` is now exactly `pull_request:` — `push:` and `workflow_dispatch:` removed
- workflow name, job id, job names and steps unchanged
- `sanity-check.yml` left alone; it already ran on `push:` to `main` only

## Why

- PR checks were running on `main`, which `✅ Sanity check` already covers
- every PR commit matched both triggers, doubling runs for no added coverage

## Verified

- `bun run ci` green
- one run per push on the PR branch, zero runs on `main`
```

## Pre-Open Checklist

Before `gh pr create` / `gh pr edit`:

- [ ] Title begins with the literal five characters `CHE: `
- [ ] Title after the prefix is lowercase, imperative, short and specific — not `fixes` / `various improvements`
- [ ] No `chore:`/`feat:`/`fix:` prefix after `CHE: `
- [ ] Title ≤72 chars total, no trailing period, no `(#N)`, no backticks
- [ ] Body has `## What`; `## Verified` present if anything was run
- [ ] Body is bullets — zero prose paragraphs beyond a 0–2 sentence lead-in
- [ ] Bullets are one line, no trailing periods, ~8 per section max
- [ ] Code tokens backticked in the body
- [ ] **Zero** mention of any AI tool/agent anywhere in title or body
- [ ] **Zero** "Generated with Claude Code" footer

Editing an existing PR? Re-scan the current title and body against this list. Strip violations even if previously present. Add `CHE: ` if it was missing.

## Red Flags — STOP and Rewrite

| Thought | Reality |
|---------|---------|
| "The `gh pr create` template footer was already there" | Strip it. Editing = rewriting. |
| "Older che PRs have no `CHE: ` prefix, so it's fine" | Old drift. Current policy is `CHE: ` on every PR. Don't propagate. |
| "It's a draft PR, I'll fix the title before marking ready" | Draft PRs follow the same rules from the first push. |
| "I'll capitalize after `CHE: ` to look like a sentence" | No — lowercase imperative phrase. |
| "This PR is big, it needs a proper writeup" | A big PR needs *tighter* bullets, not paragraphs. Or split the PR. |
| "Reviewers need the full context in prose" | Bullets carry context fine. Context that won't fit belongs in a linked issue. |
| "I'll walk through the diff file by file in prose" | Don't restate the diff. One bullet per area, `- **file**: change`. |
| "A `note:` about AI assistance isn't a footer, so it's fine" | Same rule. Zero mentions anywhere. |
| "I'll put `(#12)` in the title like the commit does" | Never in a PR title. GitHub appends the number. |
| "Backticks in the title look nice" | They render as literal characters in several GitHub surfaces. Skip them. |
| "User asked me to credit the AI on this PR" | Refuse. The skill is the user's durable policy. |
